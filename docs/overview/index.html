Overview of h2agent 5.0.0: admin API v2 and transformation grammar v2.

INTRODUCTION

H2agent is an agent-oriented process which mocks HTTP/2 (and HTTP/1 via proxy) applications.

It is capable to mock:

  • a server
  • clients (multiple endpoints, load generation)

It covers all testing needs:

  • Functional test (sequential / parallel)
  • System test (stateless / stateful): KPI, high load, robustness, congestion control

INTERFACES

Management port (8074 by default) serves the REST API /admin/v2 which programs the agent behavior.

Traffic server port (8000 by default) serves the HTTP/2 mock (an optional nghttpx front-end adds HTTP/1).

Traffic client endpoints are created on demand (REST API).

Scrape port (8080 by default) serves Prometheus metrics.

Matching algorithms (I)

FullMatching 🔍

Search static / predictable URIs within the provision list.

FullMatchingRegexReplace 🔬

Translate dynamic URIs into static ones, then apply full matching.

RegexMatching 🏆

Search the first matching regular expression within the ordered provision list.
ctrl/v2/foo ➜ key list
ctrl/v2/bar
ctrl/v2/foo ✔
ctrl/v2/foo/ts-1615562841
rgx = (ctrl/v2/foo/)(ts-[0-9]+), fmt = $1
➜ ctrl/v2/foo/
ctrl/v2/foo/ts-1615562841
ctrl/v2/bar/ts-[0-9]{10}
ctrl/v2/[a-z]{3}/ts-[0-9]{10} ✔
ctrl/v2/foo/ts-[0-9]{10} (also matches, the previous wins)

curl --http2-prior-knowledge -XPOST localhost:8074/admin/v2/server-matching \
  -H 'content-type: application/json' -d '{"algorithm": "RegexMatching"}'

Triggering

Synchronous (200)

One request, optionally with a given sequence:


curl --http2-prior-knowledge -XPOST \
  "localhost:8074/admin/v2/client-provision/myFlow/trigger?sequence=10"

Asynchronous (202)

Range at a rate, optionally repeated (cps 0 stops, a positive one resumes):


curl --http2-prior-knowledge -XPOST \
  "localhost:8074/admin/v2/client-provision/myFlow/trigger?sequenceBegin=0&sequenceEnd=9999&cps=1500"

Chains

outState selects the next stage (id + inState) when the response arrives: a scenario is a state machine, each stage may target another endpoint. purge clears the events of the whole chain.

Load

Worker pool for request preparation, pool congestion control (--traffic-client-pool-max-pending) and dispatch latency diagnostics (GET /admin/v2/client/dispatch-latency).

Flow model

server and client modes · transformation rule

from⟶ filter[ ]⟶ to
🚗
🔧 capture🏭 transform (in list order)🏁 write / act

An ordered list of rules; the first failing filter stops the chain and runs onFilterFail. Every kind is a discriminator (source, op, target) plus named fields.

sources
targets
filters
Example for server mode
Example for client mode

Rule shape


{
  "from":   {"source": "requestUriPath"},
  "filter": [
    {"op": "regexReplace", "rgx": "/app/v1/item/id-([0-9]+)", "fmt": "$1"},
    {"op": "cast", "type": "unsigned"}
  ],
  "to":     {"target": "responseBody", "path": "/id"},
  "onFilterFail": [
    {"from": {"source": "literal", "value": "404"}, "to": {"target": "responseStatusCode"}}
  ]
}
  • lowerCamelCase everywhere, one form per kind, no string shortcuts.
  • Fields named after their role: path (json pointer, absent = whole document), name, key, id, file, value, rgx / fmt.
  • Filters run in list order; typing is a filter: {"op": "cast", "type": "string|integer|unsigned|float|boolean|object|json"}.
  • Nothing is dot separated nor url-encoded any more.
  • Every rule is validated at load: GET /admin/v2/api-schema/server-provision.

Values, variables and references

Native json store

var and vault keep the json type of their values (an object stays an object, 2 is not "2"). Both admit a json pointer path.

@{name/<pointer>}

Runtime substitution of variables, also navigating into them: @{doc/a/b}, @{caps/1}. Templates are precompiled at load.

#{key[/pointer]}

Provision references resolved once at load against the vault: shared regular expressions, constants…

Boolean criterion

null, false, numeric zero and "" are false; anything else is true. Shared by conditionVar, break, clientProvision and the boolean cast.

Eraser

One meaning per target: removes the variable, the vault entry or node, the body node, empties a file, purges events. Conditional with conditionVar.

Server mode example (regex matching)


{
  "requestMethod": "GET",
  "requestUri": "/app/v1/foo/bar/([0-9]*)",
  "responseCode": 200,
  "responseBody": {"foo": "bar-1"},
  "responseHeaders": {"content-type": "text/html", "x-version": "1.0.0"},
  "transform": [
    {"from": {"source": "random", "min": 10, "max": 30},
     "to": {"target": "responseDelayMs"}},
    {"from": {"source": "strftime", "fmt": "Now it's %I:%M%p."},
     "to": {"target": "responseBody", "path": "/queryTime"}},
    {"from": {"source": "literal", "value": "[{\"id\":\"2000\"},{\"id\":\"2001\"}]"},
     "filter": [{"op": "cast", "type": "json"}],
     "to": {"target": "responseBody", "path": "/array"}},
    {"from": {"source": "requestUriPath"},
     "filter": [{"op": "regexCapture", "rgx": "/app/v1/foo/bar/([0-9]*)"}],
     "to": {"target": "responseBody", "path": "/capturedBarIdFromURI"}}
  ]
}

Behavior

A GET to /app/v1/foo/bar/56 is answered after a random delay in [10, 30] ms, with status 200, the headers given and this body:


{
  "foo": "bar-1",
  "queryTime": "Now it's 08:35PM.",
  "array": [{"id": "2000"}, {"id": "2001"}],
  "capturedBarIdFromURI": "56"
}

Client mode example (pre-send and post-response)


{
  "id": "get-foo-bar-items",
  "endpoint": "myBackend",
  "requestMethod": "GET",
  "requestUri": "/app/v1/foo/bar/items",
  "requestHeaders": {"content-type": "application/json", "x-version": "1.0.0"},
  "requestBody": {"query": "default"},
  "timeoutMs": 3000,
  "expectedResponseStatusCode": 200,
  "transform": [
    {"from": {"source": "random", "min": 10, "max": 30},
     "to": {"target": "requestDelayMs"}},
    {"from": {"source": "strftime", "fmt": "Now it's %I:%M%p."},
     "to": {"target": "requestBody", "path": "/queryTime"}},
    {"from": {"source": "literal", "value": "[{\"id\":\"2000\"},{\"id\":\"2001\"}]"},
     "filter": [{"op": "cast", "type": "json"}],
     "to": {"target": "requestBody", "path": "/items"}}
  ],
  "onResponseTransform": [
    {"from": {"source": "responseBody", "path": "/data/id"},
     "to": {"target": "vault", "key": "lastDataId"}},
    {"from": {"source": "responseHeader", "name": "x-trace-id"},
     "to": {"target": "vault", "key": "lastTraceId"}}
  ]
}

Behavior

When triggered, it sends a GET to myBackend after a random delay in [10, 30] ms, with a 3 s timeout and this body:


{
  "query": "default",
  "queryTime": "Now it's 08:35PM.",
  "items": [{"id": "2000"}, {"id": "2001"}]
}

On a 200 response, the body field /data/id and the header x-trace-id are kept in the vault (lastDataId, lastTraceId) for the next steps of the chain. Another status code is counted as unexpected.

From grammar v1 to v2


{"source": "request.uri.path",
 "target": "response.body.json.unsigned./uriId",
 "filter": {"RegexReplace": {"rgx": "/app/v1/load-test/id-([0-9]+)", "fmt": "$1"}}}
⬇️ h2agent-migrate

{"from": {"source": "requestUriPath"},
 "filter": [{"op": "regexReplace", "rgx": "/app/v1/load-test/id-([0-9]+)", "fmt": "$1"},
            {"op": "cast", "type": "unsigned"}],
 "to": {"target": "responseBody", "path": "/uriId"}}
  • Syntax-only conversion: each v2 rule behaves as its v1 origin (stores keep their json type).
  • h2agent-migrate --in v1.json --out v2.json, --reverse for diagnostics.
  • h2agent-migrate --scan ./tests finds /admin/v1 references and v1 rules in files, scripts and tests (exit code 1).
  • Admin API moves to /admin/v2; every change is listed with before / after examples in the migration guide.

Quick start


# Run the agent (traffic 8000, admin 8074, metrics 8080):
docker run --rm -d --network=host --name h2agent ghcr.io/testillano/h2agent:latest

# Provision a server answer:
curl --http2-prior-knowledge -XPOST localhost:8074/admin/v2/server-provision \
  -H 'content-type: application/json' \
  -d '{"requestMethod": "GET", "requestUri": "/hello", "responseCode": 200,
       "responseBody": {"hello": "world"}}'

# Send traffic:
curl --http2-prior-knowledge localhost:8000/hello   # {"hello":"world"}

# Inspect what was received:
curl --http2-prior-knowledge "localhost:8074/admin/v2/server-data?requestMethod=GET&requestUri=/hello&eventNumber=-1"

Helm chart for kubernetes, native build (./build-native.sh) and helper functions (source tools/helpers.bash) are also available.
